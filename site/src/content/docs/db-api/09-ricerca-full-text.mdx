## Obiettivi

- Capire la differenza tra un **filtro di sottostringa** (`LIKE '%x%'`) e una **ricerca full-text** (indice invertito, ranking).
- Usare `GET /api/v1/search` con la sintassi FTS5: parole, prefissi `*`, `AND`/`OR`/`NOT`, `"frasi"`.
- Leggere `score` e `snippet` e mostrarli in un'interfaccia.
- Gestire l'errore `400 bad_query` di una sintassi non valida.

## Teoria

### LIKE vs full-text

`GET /books?q=tri` (capitolo 4) fa in SQL `WHERE title LIKE '%tri%'`: cerca la sottostringa nel titolo. Semplice, ma:

- scandisce **tutte** le righe (niente indice: con milioni di libri è lento);
- trova `tri` dentro `Trieste`, `Sestri`, `Contro`… senza distinguere parole intere;
- non ordina per rilevanza;
- non cerca nella descrizione, né in più campi insieme, né gestisce "una parola O l'altra".

Un motore **full-text** costruisce un **indice invertito**: per ogni parola (*token*), l'elenco dei documenti che la contengono. SQLite lo offre con l'estensione **FTS5** (`CREATE VIRTUAL TABLE books_fts USING fts5(title, description)`); PostgreSQL con `tsvector`; poi ci sono motori dedicati (Elasticsearch, Meilisearch, Typesense) che aggiungono tolleranza agli errori di battitura, sinonimi, facet. Il concetto è lo stesso.

### Cosa restituisce `/search`

```json
{ "id": 7, "title": "Oltre Trieste", "price": 28.25, "author_id": 12,
  "score": -3.1252954456330926,
  "snippet": "Oltre <b>Trieste</b>. Un libro di fantascienza ambientato tra Otranto e Brisighella." }
```

- **`score`**: rilevanza secondo **BM25**, la formula standard dei motori di ricerca (frequenza del termine nel documento, rarità del termine nell'indice, lunghezza del documento). In SQLite **più basso = più rilevante** (è già negativo); i risultati arrivano ordinati.
- **`snippet`**: un estratto della descrizione con il termine trovato evidenziato tra `<b>…</b>` (il server usa la funzione `snippet()` di FTS5). Da mostrare come HTML, sanificando se il contenuto non fosse fidato.

### La sintassi delle query FTS5

| Scrivi | Trova |
|---|---|
| `trieste` | documenti con la parola *trieste* (parola intera, maiuscole ignorate) |
| `tri*` | parole che **iniziano** con *tri* (prefisso) |
| `trieste estati` | entrambe (AND implicito) |
| `trieste AND estati` | idem, esplicito (operatori in **maiuscolo**) |
| `trieste OR sestri` | almeno una |
| `trieste NOT estati` | la prima ma non la seconda |
| `"le estati"` | la **frase**, parole adiacenti in quell'ordine |
| `title:trieste` | solo nella colonna `title` |

Virgolette e parentesi sbilanciate producono un errore di sintassi: il server risponde `400 bad_query`.

## Python e TypeScript

Una funzione di ricerca che gestisce il 400 (query dell'utente scritta male) senza far crollare il programma, e stampa lo snippet convertendo `<b>` in maiuscole per il terminale.

<Tabs syncKey="lang">
<TabItem label="Python">
```python
# python3 cerca.py "trieste NOT estati"
import re, sys
import httpx

def cerca(q, limit=5):
    r = httpx.get("https://corso-api-json.giuseppebosi.com/api/v1/search", params={"q": q, "limit": limit})
    if r.status_code == 400:
        print("sintassi non valida:", r.json()["error"]["details"]["sqlite"]); return []
    r.raise_for_status()
    return r.json()["items"]

for hit in cerca(sys.argv[1] if len(sys.argv) > 1 else "trieste"):
    evidenziato = re.sub(r"<b>(.*?)</b>", lambda m: m.group(1).upper(), hit["snippet"] or "")
    print(f'{hit["score"]:7.3f}  {hit["title"]:<25} {evidenziato}')
```
</TabItem>
<TabItem label="TypeScript">
```ts
// node --experimental-strip-types cerca.ts "trieste NOT estati"
async function cerca(q: string, limit = 5) {
  const url = new URL("https://corso-api-json.giuseppebosi.com/api/v1/search");
  url.searchParams.set("q", q); url.searchParams.set("limit", String(limit));
  const r = await fetch(url);
  if (r.status === 400) { console.log("sintassi non valida:", (await r.json()).error.details.sqlite); return []; }
  if (!r.ok) throw new Error("HTTP " + r.status);
  return (await r.json()).items as { title: string; score: number; snippet: string | null }[];
}
for (const hit of await cerca(process.argv[2] ?? "trieste")) {
  const evidenziato = (hit.snippet ?? "").replace(/<b>(.*?)<\/b>/g, (_, w) => w.toUpperCase());
  console.log(hit.score.toFixed(3).padStart(7), hit.title.padEnd(25), evidenziato);
}
```

## Esercizio

1. Quanti libri contengono la parola *Ustica* (titolo o descrizione) secondo `/search`, e quanti secondo `/books?q=ustica`? Perché differiscono?
2. Trova i libri che parlano di *Sestri* **o** *Camogli* ma **non** di *Trieste*.
3. Cosa succede con `q=x` (una sola lettera)? E con `q=tr`? Spiega la differenza tra i due esiti.

<details>
<summary>Soluzione</summary>

1. `/search?q=ustica` trova anche i libri che citano Ustica solo nella descrizione ("ambientato tra … e Ustica"); `/books?q=ustica` guarda solo il titolo. I numeri dipendono dal dataset: confrontali con `jq '.items | length'` e `jq .meta.total`.
2. `q=(sestri OR camogli) NOT trieste` — le parentesi sono ammesse in FTS5.
3. `q=x` → `422 validation_error`: il server richiede almeno 2 caratteri (`min_length`). `q=tr` → `200` con zero risultati: *tr* non è una parola intera in nessun documento (servirebbe `tr*`).
</details>

## Errori comuni

- **Aspettarsi la sottostringa**: `q=tri` non trova *Trieste* (serve `tri*`).
- **Operatori minuscoli**: `trieste and estati` cerca anche la parola *and*. Vanno in MAIUSCOLO.
- **Non codificare `*` e `"`** nell'URL scritto a mano.
- **Ordinare per `score` crescente credendo che "più grande = meglio"**: in SQLite bm25 è negativo, più basso = più rilevante. I risultati arrivano già ordinati.
- **Mostrare `snippet` come testo**: vedrai `<b>` letterali.

## In sintesi

`LIKE` cerca sottostringhe scandendo tutto; FTS usa un indice invertito, capisce parole, prefissi, operatori e frasi, e ordina per rilevanza (BM25). `/search` restituisce `score` e `snippet`; una sintassi rotta è un 400. Prossimo capitolo: numeri invece di righe — aggregazioni e statistiche.
