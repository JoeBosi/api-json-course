## Obiettivi

- Leggere un errore dell'API: status, `code`, `message`, `details`.
- Sapere cosa significa ciascun codice 4xx e **cosa correggere**.
- Distinguere "errore HTTP" (c'è una risposta) da "errore di rete" (non c'è), e gestirli diversamente.
- Scrivere una funzione di chiamata che trasformi gli errori in eccezioni leggibili.

## Teoria

### Un formato unico

Ogni errore di questo server — di qualunque tipo — ha la stessa forma:

```json
{
  "error": {
    "code": "not_found",                 ← identificativo stabile, pensato per il codice (if code == …)
    "message": "Libro 9999 non trovato", ← testo per gli umani, può cambiare
    "details": …                         ← opzionale: lista di problemi (422) o oggetto con info (400)
  }
}
```

Non tutte le API sono così ordinate (alcune rispondono `{"detail": "..."}`, altre `{"message": …}`, altre HTML!). Quando ne usi una nuova, la prima cosa da fare è provocare un errore e guardare la forma.

### I codici, uno per uno

| Status | `code` tipici qui | Cosa vuol dire | Cosa fai |
|---|---|---|---|
| **400** Bad Request | `bad_sort`, `bad_expand`, `bad_query`, `unknown_field` | la richiesta è formalmente ok ma un parametro non ha senso | leggi `details.allowed` e correggi |
| **401** Unauthorized | `sandbox_required`, `unauthorized`, `invalid_token`, `expired_token`, `bad_authorization` | manca o è sbagliata l'autenticazione (il nome è fuorviante: è "non autenticato") | procurati/rinnova il token, controlla l'header |
| **403** Forbidden | `sql_not_allowed` | sei autenticato ma **non puoi** fare questo | non insistere: è una regola |
| **404** Not Found | `not_found` | la risorsa (o l'endpoint) non esiste | controlla id e percorso |
| **405** Method Not Allowed | — | l'endpoint esiste ma non con quel metodo. Questo server, per come instrada `/api/*`, risponde 404 per i metodi che il router non prevede (es. `DELETE /health`), ma 405 per `HEAD` (es. `HEAD /books/1`); altri rispondono 405 con header `Allow` | usa il metodo giusto |
| **408** Request Timeout | `sql_timeout` | il server ha smesso di aspettare (qui: query oltre 2 s) | semplifica |
| **409** Conflict | `duplicate_isbn`, `duplicate_email`, `book_in_orders`, `invalid_transition`, `out_of_stock` | la richiesta contraddice lo **stato attuale** dei dati | cambia i dati o l'ordine delle operazioni |
| **413** Payload Too Large | — | corpo troppo grande (qui Caddy limita a 1 MB) | riduci |
| **415** Unsupported Media Type | — | `Content-Type` non gestito. Questo server prova comunque a leggere il corpo come JSON e, se non ci riesce, risponde 422 | manda `application/json` |
| **422** Unprocessable Entity | `validation_error`, `unknown_author`, `unknown_category`, `unknown_book`, `empty_patch` | sintassi ok, **contenuto** non valido: campo mancante, tipo sbagliato, valore fuori intervallo, FK inesistente | leggi `details[]`: ogni voce ha `loc` (dove) e `msg` (perché) |
| **429** Too Many Requests | `rate_limited` | troppe richieste dal tuo IP (120/min) | aspetta `Retry-After` secondi, rallenta |
| **5xx** | — | ha sbagliato il server | riprova più tardi; se persiste, non è colpa tua |

<Aside type="tip" title="4xx vs 5xx nel codice">
Un 4xx è **deterministico**: rifare la stessa richiesta dà lo stesso errore, quindi il retry è inutile (eccetto 429 e 408). Un 5xx o un errore di rete possono essere transitori: un retry con attesa ha senso. Capitolo 16.
</Aside>

## Python e TypeScript

Una funzione `prendi(url)` che: restituisce i dati se tutto va bene; su errore HTTP stampa status, `code`, `message` e i dettagli; su errore di rete lo dice senza confonderlo con un errore dell'API.

<Tabs syncKey="lang">
<TabItem label="Python">
```python
# python3 errori.py
import httpx

def prendi(url):
    try:
        r = httpx.get(url, timeout=10)
        r.raise_for_status()          # solleva HTTPStatusError se lo status è 4xx o 5xx
        return r.json()
    except httpx.HTTPStatusError as e:
        errore = e.response.json()["error"]      # il formato è sempre {"error": {...}}
        print(f"{e.response.status_code} {errore['code']}: {errore['message']}")
        if isinstance(errore.get("details"), list):
            for d in errore["details"]:
                print("   -", ".".join(map(str, d["loc"])), "→", d["msg"])
    except httpx.RequestError as e:               # rete, DNS, timeout: nessuna risposta HTTP
        print("errore di rete:", e)

prendi("https://corso-api-json.giuseppebosi.com/api/v1/books/9999")
prendi("https://corso-api-json.giuseppebosi.com/api/v1/books?sort=boh")
prendi("https://corso-api-json.giuseppebosi.com/api/v1/books?limit=500")
prendi("http://localhost:1/api")                  # nessun server in ascolto
```
`httpx.HTTPStatusError` ha `.response` (con status e corpo); `httpx.RequestError` è la base di `ConnectError`, `ReadTimeout`, ecc. (`requests` ha `requests.HTTPError` e `requests.RequestException`, stessa idea).
</TabItem>
<TabItem label="TypeScript">
```ts
// node --experimental-strip-types errori.ts
async function prendi(url: string) {
  let r: Response;
  try { r = await fetch(url); }
  catch (e) { console.log("errore di rete:", (e as Error).message); return; }   // nessuna risposta HTTP
  if (!r.ok) {                                   // fetch NON lancia per 4xx/5xx: va controllato a mano
    const { error } = await r.json();
    console.log(`${r.status} ${error.code}: ${error.message}`);
    if (Array.isArray(error.details)) for (const d of error.details) console.log("   -", d.loc.join("."), "→", d.msg);
    return;
  }
  return r.json();
}
await prendi("https://corso-api-json.giuseppebosi.com/api/v1/books/9999");
await prendi("https://corso-api-json.giuseppebosi.com/api/v1/books?sort=boh");
await prendi("https://corso-api-json.giuseppebosi.com/api/v1/books?limit=500");
await prendi("http://localhost:1/api");           // nessun server in ascolto
```
`fetch` lancia (`TypeError: fetch failed`) **solo** per problemi di rete; un 500 è una risposta "riuscita" dal suo punto di vista. Per un timeout: `fetch(url, { signal: AbortSignal.timeout(10_000) })`.
</TabItem>
</Tabs>

## Esercizio

Per ciascuna situazione, scrivi lo status e il `code` che ti aspetti, poi verifica:

1. `PATCH /api/v1/books/1` con corpo `{}` (sandbox).
2. `PATCH /api/v1/orders/1` con `{"status": "pending"}` (l'ordine 1 è `delivered`).
3. `GET /api/v1/sandbox/me` con header `Authorization: Token abc`.
4. `POST /api/v1/orders` con un `book_id` che non esiste.

<details>
<summary>Soluzione</summary>

1. `422 empty_patch` — nessun campo da modificare.
2. `409 invalid_transition` — da `delivered` non si va da nessuna parte; `details.allowed` è `[]`.
3. `401 bad_authorization` — lo schema dev'essere `Bearer`.
4. `422 unknown_book` — chiave esterna inesistente, controllata prima di scrivere.
</details>

## Errori comuni

- **Leggere solo `message`** e fare `if "non trovato" in message`: i testi cambiano, i `code` no.
- **Catturare tutto con `except Exception`** e stampare "errore": perdi status e dettagli, e non distingui un 404 da un cavo staccato.
- **Ritentare un 4xx**: darà lo stesso risultato. Ritenta solo 429 (dopo `Retry-After`), 408, 5xx, errori di rete.
- **Ignorare `details` del 422**: contiene la risposta alla domanda "cosa devo correggere".

## In sintesi

Status per la famiglia, `code` per decidere, `message` per leggere, `details` per correggere. In Python `raise_for_status()` + due `except`; in TypeScript `try` intorno a `fetch` e `if (!r.ok)`. Prossimo capitolo: da dove viene quel `Bearer`, e come si tengono i segreti.
