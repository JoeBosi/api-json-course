## Obiettivi

- Creare una **sandbox** (una copia privata del database) e usarne il token in ogni richiesta di scrittura.
- Fare `POST` (creare), `PUT` (sostituire), `PATCH` (modificare in parte), `DELETE` (eliminare) e leggere le risposte: `201` + `Location`, `200`, `204`, `409`.
- Capire la differenza tra PUT e PATCH sul campo.
- Azzerare o eliminare la sandbox.

## Teoria

### Perché una sandbox

Un server pubblico su cui chiunque può scrivere diventerebbe un caos in un'ora. Questo server usa un compromesso didattico: il dataset pubblico è **in sola lettura**; chi vuole scrivere chiede un **token** con `POST /api/v1/sandbox`, e da quel momento ogni richiesta che porta quel token lavora su una **copia** del database tutta sua. Il token è un segreto: chi lo ha, vede e modifica la tua copia. Scade dopo 6 ore di inattività (ogni richiesta rinnova il timer).

Il token si manda nell'header `Authorization: Bearer <token>` (standard, [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750)) oppure `X-Sandbox-Token: <token>`. Senza token, una scrittura risponde `401` con il codice `sandbox_required`.

### I quattro verbi di scrittura

| Verbo | Sull'URL | Corpo | Risposta tipica | Idempotente |
|---|---|---|---|---|
| `POST` | la **collezione** (`/books`) | l'oggetto nuovo | `201 Created` + header `Location` con l'URL del nuovo elemento + l'oggetto creato | no |
| `PUT` | l'**elemento** (`/books/81`) | l'oggetto **completo** | `200` + l'oggetto | sì |
| `PATCH` | l'elemento | **solo i campi** da cambiare | `200` + l'oggetto | in pratica sì |
| `DELETE` | l'elemento | nessuno | `204 No Content` (corpo vuoto) | sì |

`PUT` vs `PATCH` è la distinzione che più spesso sorprende: con `PUT` **i campi che non mandi vengono azzerati** (o messi al default), perché stai sostituendo l'intera rappresentazione. Con `PATCH` restano com'erano.

### Le regole del server (validazione e integrità)

Il server non accetta qualunque cosa: `title` non vuoto, `price ≥ 0`, `author_id` e `category_id` devono **esistere** (chiavi esterne), l'ISBN dev'essere unico. Le violazioni tornano come `422` (dati non validi), `409` (conflitto con lo stato attuale: ISBN duplicato, libro presente in ordini). Capitolo 7 e 13 per i dettagli.

## Python e TypeScript

Il ciclo completo: crea sandbox → POST → PATCH → DELETE, con controllo dello status e lettura di `Location`.

<Tabs syncKey="lang">
<TabItem label="Python">
```python
# python3 scritture.py
import httpx

base = "https://corso-api-json.giuseppebosi.com/api/v1"
with httpx.Client(base_url=base) as c:
    token = c.post("/sandbox").raise_for_status().json()["token"]
    c.headers["Authorization"] = f"Bearer {token}"      # da qui in poi tutte le richieste lo portano

    nuovo = {"title": "Il mio primo libro", "author_id": 3, "category_id": 2, "price": 12.5, "tags": ["novità"]}
    r = c.post("/books", json=nuovo)       # json= serializza e mette Content-Type: application/json
    r.raise_for_status()
    print(r.status_code, r.headers["location"])        # 201 …/api/v1/books/81
    libro = r.json()

    r = c.patch(f'/books/{libro["id"]}', json={"price": 9.9})
    print(r.status_code, r.json()["price"])            # 200 9.9

    r = c.delete(f'/books/{libro["id"]}')
    print(r.status_code, repr(r.text))                 # 204 ''  ← nessun corpo

    r = c.delete("/books/1")                           # FK: è in ordini
    print(r.status_code, r.json()["error"]["code"])    # 409 book_in_orders

    c.delete("/sandbox")                               # pulizia
```
</TabItem>
<TabItem label="TypeScript">
```ts
// node --experimental-strip-types scritture.ts
const base = "https://corso-api-json.giuseppebosi.com/api/v1";
const token = (await (await fetch(base + "/sandbox", { method: "POST" })).json()).token;
const headers = { Authorization: `Bearer ${token}`, "Content-Type": "application/json" };

const nuovo = { title: "Il mio primo libro", author_id: 3, category_id: 2, price: 12.5, tags: ["novità"] };
let r = await fetch(base + "/books", { method: "POST", headers, body: JSON.stringify(nuovo) });
if (!r.ok) throw new Error("HTTP " + r.status);
console.log(r.status, r.headers.get("location"));      // 201 …/api/v1/books/81
const libro = await r.json();

r = await fetch(`${base}/books/${libro.id}`, { method: "PATCH", headers, body: JSON.stringify({ price: 9.9 }) });
console.log(r.status, (await r.json()).price);          // 200 9.9

r = await fetch(`${base}/books/${libro.id}`, { method: "DELETE", headers });
console.log(r.status, JSON.stringify(await r.text()));  // 204 ""  ← nessun corpo: niente .json()

r = await fetch(`${base}/books/1`, { method: "DELETE", headers });
console.log(r.status, (await r.json()).error.code);     // 409 book_in_orders

await fetch(base + "/sandbox", { method: "DELETE", headers });   // pulizia
```
</TabItem>
</Tabs>

<Aside type="note">
In Python `json=` fa tre cose: serializza il dict, imposta `Content-Type: application/json`, codifica in UTF-8. In JavaScript le fai a mano: `JSON.stringify` + l'header. Dimenticare l'header è l'errore più frequente.
</Aside>

## Esercizio

1. Crea un cliente (`POST /api/v1/customers` con `name`, `email`, `city`), poi crea un **secondo** cliente con la stessa email. Che status ottieni e con quale `code`?
2. Crea un libro, poi fagli un `PUT` che contiene solo `title`, `author_id`, `category_id`, `price`. Confronta `attributes` prima e dopo. Poi rifai la stessa modifica del titolo con `PATCH` su un libro nuovo: cosa cambia?
3. Cancella la sandbox e riprova un `GET /api/v1/sandbox/me` con il vecchio token.

<details>
<summary>Soluzione</summary>

1. `409 Conflict`, `code: "duplicate_email"`: l'email è unica nella tabella.
2. Dopo il `PUT`, `attributes` è `{}` e `tags` è `[]`; dopo il `PATCH` sono intatti. Regola: PUT = "ecco com'è ora l'oggetto, per intero".
3. `401` con `code: "invalid_token"`: la copia non esiste più.
</details>

## Errori comuni

- **`.json()` su un 204**: corpo vuoto → `JSONDecodeError` / `SyntaxError: Unexpected end of JSON input`. Controlla lo status prima.
- **PUT con corpo parziale** credendo che sia un PATCH: dati azzerati.
- **Token tra apici singoli** in curl (`'Bearer $TOKEN'`): 401.
- **Riusare un id dopo il reset**: `POST /sandbox/reset` riporta gli id al dataset iniziale; il libro 81 non esiste più.
- **Condividere il token** (in uno screenshot, in un repo): chiunque può scrivere nella tua copia.

## In sintesi

`POST /sandbox` → token → `Authorization: Bearer`. POST crea (201 + Location), PUT sostituisce, PATCH ritocca, DELETE elimina (204). Le chiavi esterne proteggono i dati (409). Prossimo capitolo: tutti gli errori che un'API può rispondere, e come gestirli nel codice.
