## Obiettivi

- Leggere lo schema di un database attraverso l'API: tabelle, chiavi primarie (PK), chiavi esterne (FK).
- Riconoscere i tre tipi di relazione — **1-N**, **N-N**, **gerarchica** — e vedere come l'API li espone.

- Capire il problema **N+1** e perché `expand` (o un join) lo risolve.
- Fare un join **lato client** quando l'API non offre l'espansione.

## Teoria

### Chiavi primarie e chiavi esterne

In un database relazionale ogni riga di una tabella ha una **chiave primaria** (PK): un valore unico che la identifica, quasi sempre una colonna `id`. Quando una riga deve "puntare" a una riga di un'altra tabella, contiene il valore della PK di quella riga in una colonna detta **chiave esterna** (FK): `books.author_id` contiene l'`id` di una riga di `authors`.

```
authors                     books
┌────┬────────────────┐     ┌────┬──────────────────────┬───────────┐
│ id │ name           │     │ id │ title                │ author_id │
├────┼────────────────┤     ├────┼──────────────────────┼───────────┤
│ 19 │ Laura Esposito │◄────│  1 │ Il silenzio di Ustica│    19     │
│  4 │ Tomás Aldana   │◄──┬─│ 57 │ Le estati a Trieste  │     4     │
└────┴────────────────┘   └─│ 47 │ Contro Vieste        │     4     │
   PK                       └────┴──────────────────────┴───────────┘
                               PK                          FK → authors.id
```

Il database **garantisce** che una FK punti a una riga esistente (*integrità referenziale*): non puoi inserire un libro con `author_id = 999` se l'autore 999 non c'è, e non puoi cancellare un autore che ha libri (o, a seconda della regola, i libri vengono cancellati a cascata). Lo vedrai come errore 422/409 nell'API (capitolo 13).

### I tre tipi di relazione

| Tipo | Come si realizza | Nel dataset |
|---|---|---|
| **1-N** (uno a molti) | una FK nella tabella "molti" | un autore → molti libri (`books.author_id`); un cliente → molti ordini (`orders.customer_id`); un libro → molte recensioni (`reviews.book_id`) |
| **N-N** (molti a molti) | una **tabella ponte** con due FK | libri ↔ tag tramite `book_tags(book_id, tag_id)`; ordini ↔ libri tramite `order_items(order_id, book_id, quantity, unit_price)` — la tabella ponte può avere dati propri |
| **gerarchica** (auto-relazione) | una FK verso la **stessa** tabella | `categories.parent_id → categories.id`: "Gialli" sta sotto "Narrativa" |

### Come l'API espone le relazioni

Quattro modi, dal più semplice al più potente:

1. **L'id nudo**: `"author_id": 19`. Il client sa che deve fare `GET /authors/19` se vuole il nome.
2. **Risorse annidate**: `GET /authors/19/books` — "i libri dell'autore 19". L'URL segue la FK al contrario (dal padre ai figli).
3. **Espansione**: `GET /books/1?expand=author,category` — il server sostituisce (o affianca) l'id con l'oggetto intero. Una richiesta invece di tre.
4. **Filtri su relazione**: `GET /books?category=narrativa` include le sottocategorie: il server usa una query ricorsiva sulla gerarchia.

### Il problema N+1

Vuoi stampare i 20 libri di una pagina con il nome dell'autore. Con il modo 1 fai **1** richiesta per la lista + **20** per gli autori = 21 richieste (N+1). Con 1.000 libri, 1.001. È il bug di performance più comune nei client di API (e negli ORM). Soluzioni: `expand` (il server fa un JOIN), oppure scaricare **una volta** la tabella piccola (gli autori sono 20) e fare il join in memoria.

### Tre tabelle in una richiesta: un ordine con righe, libri e cliente

`orders` → `order_items` (1-N) → `books` (FK `book_id`) → `authors` (FK `author_id`), più `customers` (FK `customer_id`). Con `expand=items.book,customer` il server percorre tutta la catena:

## Python e TypeScript

Due tecniche: **expand** per l'ordine (una richiesta) e **join lato client** per i libri di un autore con il nome della categoria (le categorie sono 10: si scaricano una volta e si indicizzano per `id`).

<Tabs syncKey="lang">
<TabItem label="Python">
```python
# python3 relazioni.py
import httpx

base = "https://corso-api-json.giuseppebosi.com/api/v1"
with httpx.Client(base_url=base) as c:
    # 1. expand: l'ordine con righe, libri e cliente in UNA richiesta
    o = c.get("/orders/1", params={"expand": "items.book,customer"}).raise_for_status().json()
    print(f'Ordine {o["id"]} di {o["customer"]["name"]} ({o["customer"]["city"]}), stato {o["status"]}')
    for riga in o["items"]:
        print(f'  {riga["quantity"]} x {riga["book"]["title"]} di {riga["book"]["author_name"]} @ {riga["unit_price"]} €')

    # 2. join lato client: dizionario id -> nome, poi lookup per ogni libro (niente N+1)
    categorie = {cat["id"]: cat["name"] for cat in c.get("/categories").json()["items"]}
    autore = c.get("/authors/4").raise_for_status().json()
    libri = c.get("/authors/4/books", params={"limit": 100}).json()["items"]
    print(f'\n{autore["name"]} ({autore["country"]}): {len(libri)} libri')
    for b in libri:
        print(f'  {b["published_year"]}  {b["title"]:<30} [{categorie[b["category_id"]]}]')
```
</TabItem>

```ts
// node --experimental-strip-types relazioni.ts
const base = "https://corso-api-json.giuseppebosi.com/api/v1";
const get = async (p: string) => {
  const r = await fetch(base + p);
  if (!r.ok) throw new Error("HTTP " + r.status);
  return r.json();
};

// 1. expand: l'ordine con righe, libri e cliente in UNA richiesta
const o = await get("/orders/1?expand=items.book,customer");
console.log(`Ordine ${o.id} di ${o.customer.name} (${o.customer.city}), stato ${o.status}`);
for (const riga of o.items) console.log(`  ${riga.quantity} x ${riga.book.title} di ${riga.book.author_name} @ ${riga.unit_price} €`);

// 2. join lato client: Map id -> nome, poi lookup per ogni libro (niente N+1)
const categorie = new Map<number, string>((await get("/categories")).items.map((c: any) => [c.id, c.name]));
const autore = await get("/authors/4");
const libri = (await get("/authors/4/books?limit=100")).items;
console.log(`\n${autore.name} (${autore.country}): ${libri.length} libri`);
for (const b of libri) console.log(`  ${b.published_year}  ${b.title.padEnd(30)} [${categorie.get(b.category_id)}]`);
```

Totale richieste: 1 + 3 = **4**, indipendentemente da quanti libri ha l'autore. La versione ingenua (una `GET /categories/{id}` per libro) ne farebbe 1 + 2 + N.

<Aside type="tip" title="Quando usare cosa">
`expand` quando il server lo offre e ti servono pochi oggetti collegati. Join lato client quando la tabella collegata è piccola e la scarichi comunque (categorie, stati, valute). Per query davvero multi-tabella con aggregazioni: capitolo 12, SQL via API.
</Aside>

## Esercizio

1. Usando **solo** `/api/v1/schema`, elenca la catena di chiavi esterne che collega `reviews` a `authors` (passando per `books`).
2. Scrivi uno script che, per l'ordine 2, stampi il nome del **cliente** e, per ogni riga, il **titolo** del libro e la **categoria** (nome) del libro. Suggerimento: `expand=items.book,customer` non include la categoria del libro — ti serve un secondo passo. Quante richieste fai in tutto?

<details>
<summary>Soluzione</summary>

1. `reviews.book_id → books.id`, poi `books.author_id → authors.id`. (E `reviews.customer_id → customers.id` è un'altra strada, verso i clienti.)
2. Due strategie: (a) `expand=items.book,customer` + una `GET /books/{id}?expand=category` per riga → 1 + N richieste; (b) `expand=items.book,customer` + `GET /categories` una volta + `GET /books/{id}` per avere `category_id`… ancora N. La strada migliore con questa API: `expand=items,customer` e poi `GET /books?…` è filtrabile solo per un autore/categoria, non per lista di id; quindi la soluzione **corretta e minima** è la (a) per ordini piccoli, oppure il capitolo 12 (`POST /sql` con un JOIN su quattro tabelle) per farlo in una sola richiesta. Il punto dell'esercizio è proprio accorgersi del limite: un'API REST "a risorse" a volte richiede più round-trip di quanto vorresti.
</details>

## Errori comuni

- **Confondere `author_id` (FK) con `id` (PK)**: `GET /authors/{book.id}` dà l'autore sbagliato o un 404.
- **Espansione non supportata**: `expand=publisher` → 400 `bad_expand`, con `details.allowed`. Leggi l'elenco.
- **N+1 nascosto**: un `for` che fa una `GET` per elemento. Se vedi un loop con dentro `fetch`/`get`, chiediti se c'è un `expand` o una tabella da scaricare una volta.
- **Contare i figli con `books_count` della categoria padre**: il campo conta solo i libri diretti; per il totale ricorsivo usa `/categories/{slug}/books` o `/books?category=`.

## In sintesi

PK identifica, FK collega. 1-N = una FK; N-N = tabella ponte; gerarchia = FK su se stessa. L'API le espone con id nudi, risorse annidate, `expand` (anche a più livelli: `items.book`) e filtri ricorsivi. Evita l'N+1. Nel prossimo capitolo iniziamo a **scrivere**: sandbox e CRUD.
