## Goals

- Read a database schema through the API: tables, primary keys (PK), foreign keys (FK).
- Recognize the three kinds of relation — **1-N**, **N-N**, **hierarchical** — and see how the API exposes them.
- Use nested resources (`/authors/1/books`) and `?expand=` to follow foreign keys.
- Understand the **N+1** problem and why `expand` (or a join) solves it.
- Do a **client-side** join when the API does not offer expansion.

## Theory

### Primary keys and foreign keys

In a relational database every row of a table has a **primary key** (PK): a unique value that identifies it, almost always an `id` column. When a row has to "point" to a row of another table, it holds the value of that row's PK in a column called a **foreign key** (FK): `books.author_id` holds the `id` of a row in `authors`.

```
authors                     books
┌────┬────────────────┐     ┌────┬──────────────────────┬───────────┐
│ id │ name           │     │ id │ title                │ author_id │
├────┼────────────────┤     ├────┼──────────────────────┼───────────┤
│ 19 │ Laura Esposito │◄────│  1 │ Il silenzio di Ustica│    19     │
│  4 │ Tomás Aldana   │◄──┬─│ 57 │ Le estati a Trieste  │     4     │
└────┴────────────────┘   └─│ 47 │ Contro Vieste        │     4     │
   PK                       └────┴──────────────────────┴───────────┘
                               PK                          FK → authors.id
```

The database **guarantees** that an FK points to an existing row (*referential integrity*): you cannot insert a book with `author_id = 999` if author 999 does not exist, and you cannot delete an author who has books (or, depending on the rule, the books are deleted in cascade). You will see it as a 422/409 error in the API (chapter 13).

### The three kinds of relation

| Kind | How it is built | In the dataset |
|---|---|---|
| **1-N** (one to many) | an FK in the "many" table | an author → many books (`books.author_id`); a customer → many orders (`orders.customer_id`); a book → many reviews (`reviews.book_id`) |
| **N-N** (many to many) | a **join table** with two FKs | books ↔ tags through `book_tags(book_id, tag_id)`; orders ↔ books through `order_items(order_id, book_id, quantity, unit_price)` — the join table can have data of its own |
| **hierarchical** (self-relation) | an FK to the **same** table | `categories.parent_id → categories.id`: "Gialli" (crime) sits under "Narrativa" (fiction) |

### How the API exposes relations

Four ways, from the simplest to the most powerful:

1. **The bare id**: `"author_id": 19`. The client knows it has to call `GET /authors/19` if it wants the name.
2. **Nested resources**: `GET /authors/19/books` — "the books of author 19". The URL follows the FK backwards (from parent to children).
3. **Expansion**: `GET /books/1?expand=author,category` — the server replaces (or places next to it) the id with the whole object. One request instead of three.
4. **Filters on a relation**: `GET /books?category=narrativa` includes the subcategories: the server uses a recursive query over the hierarchy.

### The N+1 problem

You want to print the 20 books of a page with the author's name. With way 1 you make **1** request for the list + **20** for the authors = 21 requests (N+1). With 1,000 books, 1,001. It is the most common performance bug in API clients (and in ORMs). Solutions: `expand` (the server does a JOIN), or download the small table **once** (there are 20 authors) and do the join in memory.

### Three tables in one request: an order with lines, books and customer

`orders` → `order_items` (1-N) → `books` (FK `book_id`) → `authors` (FK `author_id`), plus `customers` (FK `customer_id`). With `expand=items.book,customer` the server walks the whole chain:

## Python and TypeScript

Two techniques: **expand** for the order (one request) and a **client-side join** for an author's books with the category name (there are 10 categories: download them once and index them by `id`).

<Tabs syncKey="lang">
<TabItem label="Python">
```python
# python3 relazioni.py
import httpx

base = "https://corso-api-json.giuseppebosi.com/api/v1"
with httpx.Client(base_url=base) as c:
    # 1. expand: l'ordine con righe, libri e cliente in UNA richiesta
    o = c.get("/orders/1", params={"expand": "items.book,customer"}).raise_for_status().json()
    print(f'Ordine {o["id"]} di {o["customer"]["name"]} ({o["customer"]["city"]}), stato {o["status"]}')
    for riga in o["items"]:
        print(f'  {riga["quantity"]} x {riga["book"]["title"]} di {riga["book"]["author_name"]} @ {riga["unit_price"]} €')

    # 2. join lato client: dizionario id -> nome, poi lookup per ogni libro (niente N+1)
    categorie = {cat["id"]: cat["name"] for cat in c.get("/categories").json()["items"]}
    autore = c.get("/authors/4").raise_for_status().json()
    libri = c.get("/authors/4/books", params={"limit": 100}).json()["items"]
    print(f'\n{autore["name"]} ({autore["country"]}): {len(libri)} libri')
    for b in libri:
        print(f'  {b["published_year"]}  {b["title"]:<30} [{categorie[b["category_id"]]}]')
```
</TabItem>

// node --experimental-strip-types relazioni.ts
const base = "https://corso-api-json.giuseppebosi.com/api/v1";
const get = async (p: string) => {
  const r = await fetch(base + p);
  if (!r.ok) throw new Error("HTTP " + r.status);
  return r.json();
};

// 1. expand: l'ordine con righe, libri e cliente in UNA richiesta
const o = await get("/orders/1?expand=items.book,customer");
console.log(`Ordine ${o.id} di ${o.customer.name} (${o.customer.city}), stato ${o.status}`);
for (const riga of o.items) console.log(`  ${riga.quantity} x ${riga.book.title} di ${riga.book.author_name} @ ${riga.unit_price} €`);

// 2. join lato client: Map id -> nome, poi lookup per ogni libro (niente N+1)

const autore = await get("/authors/4");
const libri = (await get("/authors/4/books?limit=100")).items;

Total requests: 1 + 3 = **4**, regardless of how many books the author has. The naive version (one `GET /categories/{id}` per book) would make 1 + 2 + N.

<Aside type="tip" title="When to use which">
`expand` when the server offers it and you need a few linked objects. A client-side join when the linked table is small and you download it anyway (categories, statuses, currencies). For truly multi-table queries with aggregations: chapter 12, SQL over the API.
</Aside>

1. Using **only** `/api/v1/schema`, list the chain of foreign keys that links `reviews` to `authors` (going through `books`).
2. Write a script that, for order 2, prints the **customer**'s name and, for each line, the book **title** and the book's **category** (name). Hint: `expand=items.book,customer` does not include the book's category — you need a second step. How many requests do you make in all?

<details>
<summary>Solution</summary>

1. `reviews.book_id → books.id`, then `books.author_id → authors.id`. (And `reviews.customer_id → customers.id` is another road, towards the customers.)
2. Two strategies: (a) `expand=items.book,customer` + one `GET /books/{id}?expand=category` per line → 1 + N requests; (b) `expand=items.book,customer` + `GET /categories` once + `GET /books/{id}` to get `category_id`… still N. The best road with this API: `expand=items,customer`, and then `GET /books?…` can only be filtered by one author/category, not by a list of ids; so the **correct and minimal** solution is (a) for small orders, or chapter 12 (`POST /sql` with a JOIN over four tables) to do it in a single request. The point of the exercise is precisely to notice the limit: a "resource-based" REST API sometimes needs more round trips than you would like.
</details>

## Common mistakes

- **Confusing `author_id` (FK) with `id` (PK)**: `GET /authors/{book.id}` gives the wrong author or a 404.
- **Unsupported expansion**: `expand=publisher` → 400 `bad_expand`, with `details.allowed`. Read the list.
- **Hidden N+1**: a `for` that makes one `GET` per element. If you see a loop with a `fetch`/`get` inside, ask yourself whether there is an `expand` or a table to download once.
- **Counting children with the parent category's `books_count`**: that field counts direct books only; for the recursive total use `/categories/{slug}/books` or `/books?category=`.

## Summary

A PK identifies, an FK links. 1-N = one FK; N-N = a join table; hierarchy = an FK onto itself. The API exposes them with bare ids, nested resources, `expand` (even on several levels: `items.book`) and recursive filters. Avoid N+1. In the next chapter we start **writing**: sandbox and CRUD.
