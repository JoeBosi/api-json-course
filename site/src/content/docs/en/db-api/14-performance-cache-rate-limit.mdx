## Goals

- Use `ETag` and `If-None-Match` so you do not download again what has not changed (`304`).
- Read `Cache-Control` and understand what can be cached, and by whom.
- See compression at work and know who applies it.
- Reuse the TCP/TLS connection (keep-alive) instead of opening one per request.
- Recognize `429 Too Many Requests` + `Retry-After` and behave well.

## Theory

A fast API is made of three things: **not doing** useless work (caching), **transferring fewer bytes** (compression), **not paying again** for fixed costs (connections). And a fourth: **protecting itself** from those who abuse it (rate limiting), because one client's slowness becomes everybody's slowness.

### ETags and conditional requests

An **ETag** (*entity tag*) is a fingerprint of the response, for example the hash of the JSON. The server sends it in the `ETag` header; on the next request the client sends it back in `If-None-Match`. If the resource is identical, the server answers **`304 Not Modified` with no body**: a few bytes instead of the whole document. The client uses the copy it had.

### Cache-Control

It says **who** may keep the response and **for how long**:

| Value | Meaning |
|---|---|
| `public, max-age=60` | anyone (browser, proxy, CDN) may keep it for 60 seconds |
| `private, max-age=…` | only the user's browser, not shared proxies |
| `no-cache` | can be kept, but must be revalidated (with the ETag) before reuse |
| `no-store` | never keep it (personal data, responses with a token) |

On the test server only `GET /books/{id}` without a token answers `public, max-age=60`; everything else (lists, statistics, and any request carrying the token) is `no-store`: your sandbox is yours.

### Compression

With `Accept-Encoding: gzip, zstd` the client declares what it can decompress; the server (or the reverse proxy in front of it) compresses and answers `Content-Encoding: gzip`. JSON compresses very well (often 5-10 times). Here compression is done by **the API itself** (FastAPI's `GZipMiddleware`), so you also see it locally with `uvicorn` alone: `/books?limit=100` goes from about 29,500 to 4,100 bytes. In production **Caddy** sits in front and can replace it with `zstd`.

### Keep-alive

Opening an HTTPS connection costs: TCP + TLS handshake, tens of milliseconds and a few round trips. HTTP/1.1 keeps the connection open (**keep-alive**) and reuses it for the next requests; HTTP/2 multiplexes them. But the client must **reuse the same object** (`httpx.Client`, a `fetch` with a shared agent): "throwaway" calls open a connection every time.

### Rate limit

The server counts the requests per IP address within a time window; above the threshold it answers `429 Too Many Requests` with `Retry-After: <seconds>`. A polite client **waits** that long and retries; a rude one insists and stays blocked longer. The public test server's limit is 30 requests per minute per IP (120 locally).

<Aside type="note" title="Rate limiting is a feature">
It is not hostility: it is what lets a small server serve many readers. A client that handles 429s with backoff is a quality client (chapter 16).
</Aside>

### Rate limit: triggering a 429 with judgment

There is no need to hammer the server to see it. A loop of just over 30 requests is enough, once:

<Curl cmd={`for i in $(seq 1 40); do
  curl -s -o /dev/null -w '%{http_code}\\n' https://corso-api-json.giuseppebosi.com/api/v1/health
done | sort | uniq -c`} spiega={[
  ['$(seq 1 40)', 'generates the numbers from 1 to 40: the loop runs 40 times'],
  ["-w '%{http_code}\\n'", 'prints only the status code of each request'],
  ['| sort | uniq -c', 'sorts the statuses and counts how many times each one appears'],
]} />

```text
     30 200
     10 429
```

Let's look at a full `429` response (from a local instance of the server configured with a `5/minute` limit, so as not to disturb the public one):

```http
HTTP/1.1 429 Too Many Requests
content-type: application/json
retry-after: 10

{"error":{"code":"rate_limited","message":"Troppe richieste: limite 5 per 1 minute. Riprova tra poco."}}
```

`Retry-After: 10` is the instruction for the client: wait 10 seconds. The body has the usual `error` format. After the loop, **wait a minute** before carrying on with the exercises.

## Python and TypeScript

A client that reuses the connection, keeps ETags per URL and respects `Retry-After`:

<Tabs syncKey="lang">
<TabItem label="Python">
```python
# pip install httpx   →   python3 cache.py
import time

import httpx

BASE = "https://corso-api-json.giuseppebosi.com/api/v1"
cache: dict[str, tuple[str, dict]] = {}          # url -> (etag, json)

# un solo Client = una sola connessione riusata (keep-alive) e header comuni
client = httpx.Client(base_url=BASE, timeout=10, headers={"Accept-Encoding": "gzip, zstd"})


def get(path: str) -> dict:
    headers = {}
    if path in cache:
        headers["If-None-Match"] = cache[path][0]      # "ho già questa versione"
    while True:
        r = client.get(path, headers=headers)
        if r.status_code == 429:
            attesa = int(r.headers.get("Retry-After", "5"))
            print(f"429: aspetto {attesa}s")
            time.sleep(attesa)
            continue
        break
    if r.status_code == 304:
        print(f"{path}: 304, uso la cache")
        return cache[path][1]
    r.raise_for_status()
    if etag := r.headers.get("ETag"):
        cache[path] = (etag, r.json())
    print(f"{path}: {r.status_code}, {len(r.content)} byte, encoding={r.headers.get('Content-Encoding', '-')}, "
          f"cache-control={r.headers.get('Cache-Control')}")
    return r.json()


t0 = time.perf_counter()
libro = get("/books/7")
libro = get("/books/7")                     # seconda volta: 304
print(libro["title"], f"({(time.perf_counter() - t0) * 1000:.0f} ms per due richieste sulla stessa connessione)")
```

<TabItem label="TypeScript">
```ts
// node --experimental-strip-types cache.ts
const BASE = "https://corso-api-json.giuseppebosi.com/api/v1";
const cache = new Map<string, { etag: string; body: unknown }>();   // url -> versione conosciuta
const dormi = (s: number) => new Promise((r) => setTimeout(r, s * 1000));

// fetch di Node riusa le connessioni (keep-alive) per la stessa origine: nessun setup extra
async function get(path: string): Promise<any> {
  const headers: Record<string, string> = { "Accept-Encoding": "gzip, zstd" };
  const noto = cache.get(path);
  if (noto) headers["If-None-Match"] = noto.etag;            // "ho già questa versione"
  for (;;) {
    const r = await fetch(BASE + path, { headers });
    if (r.status === 429) {
      const attesa = Number(r.headers.get("Retry-After") ?? 5);
      console.log(`429: aspetto ${attesa}s`);
      await dormi(attesa);
      continue;
    }
    if (r.status === 304) { console.log(`${path}: 304, uso la cache`); return noto!.body; }
    if (!r.ok) throw new Error(`HTTP ${r.status}`);
    const body = await r.json();
    const etag = r.headers.get("ETag");
    if (etag) cache.set(path, { etag, body });
    console.log(`${path}: ${r.status}, encoding=${r.headers.get("content-encoding") ?? "-"}, cache-control=${r.headers.get("cache-control")}`);
    return body;
  }
}

const t0 = performance.now();
let libro = await get("/books/7");
libro = await get("/books/7");                                // seconda volta: 304
console.log(libro.title, `(${(performance.now() - t0).toFixed(0)} ms per due richieste)`);
```

## Common mistakes

- **A "bare" `httpx.get` / `fetch` for every call in a loop**: no keep-alive, no ETag cache, no common headers.
- **Caching `no-store` responses** (with a token): private data ending up in a shared cache.
- **Retrying immediately on a 429** (or on a 5xx): it makes the problem worse. You need to wait, preferably longer each time.
- **Taking compression for granted**: here the API applies it itself, but many APIs leave it to the reverse proxy, and in development, with no proxy, there is none. Check `content-encoding`.

## Summary

ETag/304 avoid downloading again, `Cache-Control` says who may keep what, compression cuts the bytes, keep-alive removes handshakes, and `429` + `Retry-After` regulate traffic. In the next chapter you will see the API's defenses from the other side: injections, validation, CORS and secrets.
