## Goals

- Read an API error: status, `code`, `message`, `details`.
- Know what each 4xx code means and **what to fix**.
- Tell an "HTTP error" (there is a response) from a "network error" (there is none), and handle them differently.
- Write a calling function that turns errors into readable exceptions.

## Theory

### A single format

Every error from this server — of any kind — has the same shape:

```json
{
  "error": {
    "code": "not_found",                 ← identificativo stabile, pensato per il codice (if code == …)
    "message": "Libro 9999 non trovato", ← testo per gli umani, può cambiare
    "details": …                         ← opzionale: lista di problemi (422) o oggetto con info (400)
  }
}
```

Not all APIs are this tidy (some answer `{"detail": "..."}`, others `{"message": …}`, others HTML!). When you use a new one, the first thing to do is to cause an error and look at its shape.

### The codes, one by one

| Status | Typical `code` here | What it means | What you do |
|---|---|---|---|
| **400** Bad Request | `bad_sort`, `bad_expand`, `bad_query`, `unknown_field` | the request is formally fine but a parameter makes no sense | read `details.allowed` and fix it |
| **401** Unauthorized | `sandbox_required`, `unauthorized`, `invalid_token`, `expired_token`, `bad_authorization` | authentication is missing or wrong (the name is misleading: it means "not authenticated") | get/renew the token, check the header |
| **403** Forbidden | `sql_not_allowed` | you are authenticated but you **may not** do this | do not insist: it is a rule |
| **404** Not Found | `not_found` | the resource (or the endpoint) does not exist | check the id and the path |
| **405** Method Not Allowed | — | the endpoint exists but not with that method. This server, because of how it routes `/api/*`, answers 404 for methods the router does not know (e.g. `DELETE /health`), but 405 for `HEAD` (e.g. `HEAD /books/1`); others answer 405 with an `Allow` header | use the right method |
| **408** Request Timeout | `sql_timeout` | the server stopped waiting (here: a query over 2 s) | simplify |
| **409** Conflict | `duplicate_isbn`, `duplicate_email`, `book_in_orders`, `invalid_transition`, `out_of_stock` | the request contradicts the **current state** of the data | change the data or the order of operations |
| **413** Payload Too Large | — | body too large (here Caddy limits it to 1 MB) | reduce it |
| **415** Unsupported Media Type | — | `Content-Type` not handled. This server tries to read the body as JSON anyway and, if it cannot, answers 422 | send `application/json` |
| **422** Unprocessable Entity | `validation_error`, `unknown_author`, `unknown_category`, `unknown_book`, `empty_patch` | syntax ok, **content** not valid: missing field, wrong type, value out of range, nonexistent FK | read `details[]`: each entry has `loc` (where) and `msg` (why) |
| **429** Too Many Requests | `rate_limited` | too many requests from your IP (30/min on the public server) | wait `Retry-After` seconds, slow down |
| **5xx** | — | the server got it wrong | retry later; if it persists, it is not your fault |

<Aside type="tip" title="4xx vs 5xx in code">
A 4xx is **deterministic**: repeating the same request gives the same error, so retrying is pointless (except for 429 and 408). A 5xx or a network error can be transient: a retry after a wait makes sense. Chapter 16.
</Aside>

The 422 lists **all** the problems at once: fix them all before retrying. And malformed JSON?

<Curl cmd={`curl -sS -X POST https://corso-api-json.giuseppebosi.com/api/v1/books \\
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \\

  ['{"title": "x",}', 'a trailing comma: it is not JSON. The server cannot even read it'],

```json
{"error":{"code":"validation_error","message":"Richiesta non valida: controlla i campi in details","details":[{"loc":["body",14],"msg":"JSON decode error","type":"json_invalid"}]}}
```

`loc: ["body", 14]` = character 14 of the body: the point where the parser gets stuck, that is the closing brace right after the extra comma.

You already saw 401 and 409 in chapter 6; you will only see 429 if you overdo it: it answers `Retry-After: 10` and `{"error":{"code":"rate_limited",…}}`. No need to trigger it on purpose.

## Python and TypeScript

A function `prendi(url)` that: returns the data if all goes well; on an HTTP error prints status, `code`, `message` and the details; on a network error says so without confusing it with an API error.

<Tabs syncKey="lang">
<TabItem label="Python">
```python
# python3 errori.py
import httpx

def prendi(url):
    try:
        r = httpx.get(url, timeout=10)
        r.raise_for_status()          # solleva HTTPStatusError se lo status è 4xx o 5xx
        return r.json()
    except httpx.HTTPStatusError as e:
        errore = e.response.json()["error"]      # il formato è sempre {"error": {...}}
        print(f"{e.response.status_code} {errore['code']}: {errore['message']}")
        if isinstance(errore.get("details"), list):
            for d in errore["details"]:
                print("   -", ".".join(map(str, d["loc"])), "→", d["msg"])
    except httpx.RequestError as e:               # rete, DNS, timeout: nessuna risposta HTTP
        print("errore di rete:", e)

prendi("https://corso-api-json.giuseppebosi.com/api/v1/books/9999")
prendi("https://corso-api-json.giuseppebosi.com/api/v1/books?sort=boh")
prendi("https://corso-api-json.giuseppebosi.com/api/v1/books?limit=500")
prendi("http://localhost:1/api")                  # nessun server in ascolto
```

`httpx.HTTPStatusError` has `.response` (with status and body); `httpx.RequestError` is the base of `ConnectError`, `ReadTimeout`, etc. (`requests` has `requests.HTTPError` and `requests.RequestException`, same idea).
</TabItem>
<TabItem label="TypeScript">
```ts
// node --experimental-strip-types errori.ts
async function prendi(url: string) {
  let r: Response;
  try { r = await fetch(url); }
  catch (e) { console.log("errore di rete:", (e as Error).message); return; }   // nessuna risposta HTTP
  if (!r.ok) {                                   // fetch NON lancia per 4xx/5xx: va controllato a mano
    const { error } = await r.json();
    console.log(`${r.status} ${error.code}: ${error.message}`);
    if (Array.isArray(error.details)) for (const d of error.details) console.log("   -", d.loc.join("."), "→", d.msg);
    return;
  }
  return r.json();
}
await prendi("https://corso-api-json.giuseppebosi.com/api/v1/books/9999");
await prendi("https://corso-api-json.giuseppebosi.com/api/v1/books?sort=boh");
await prendi("https://corso-api-json.giuseppebosi.com/api/v1/books?limit=500");
await prendi("http://localhost:1/api");           // nessun server in ascolto
```

`fetch` throws (`TypeError: fetch failed`) **only** for network problems; a 500 is a "successful" response from its point of view. For a timeout: `fetch(url, { signal: AbortSignal.timeout(10_000) })`.
</TabItem>
</Tabs>

<details>
<summary>Solution</summary>

1. `422 empty_patch` — no field to change.
2. `409 invalid_transition` — from `delivered` you cannot go anywhere; `details.allowed` is `[]`.
3. `401 bad_authorization` — the scheme must be `Bearer`.
4. `422 unknown_book` — a nonexistent foreign key, checked before writing.
</details>

## Common mistakes

- **Reading only `message`** and doing `if "non trovato" in message`: texts change, `code`s do not.
- **Catching everything with `except Exception`** and printing "error": you lose status and details, and cannot tell a 404 from an unplugged cable.
- **Retrying a 4xx**: it will give the same result. Retry only 429 (after `Retry-After`), 408, 5xx and network errors.
- **Ignoring the 422's `details`**: it holds the answer to "what do I need to fix".

## Summary

Status for the family, `code` to decide, `message` to read, `details` to fix. In Python `raise_for_status()` + two `except`s; in TypeScript a `try` around `fetch` and `if (!r.ok)`. Next chapter: where that `Bearer` comes from, and how secrets are kept.
