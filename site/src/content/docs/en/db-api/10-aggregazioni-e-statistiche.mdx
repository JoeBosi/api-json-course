## Goals

- Understand what an API does when it returns "statistics": `COUNT`, `SUM`, `AVG`, `MIN`, `MAX` computed by the database.
- Read an aggregated response and know which tables and JOINs it comes from.
- Use `GET /stats` and `GET /stats/sales?group_by=…&from=…&to=…` with curl, Python and TypeScript.
- Draw a text chart from the aggregated numbers.

## Theory

So far you have asked for **rows**: a book, a list of orders. Aggregations ask instead for **summary numbers** over many rows: how many books per category, revenue per month, an author's average rating. In SQL you get them with **aggregate functions** and `GROUP BY`:

| Function | What it computes | Example in the dataset |
|---|---|---|
| `COUNT(*)` | number of rows in the group | books per category |
| `COUNT(DISTINCT x)` | distinct values | distinct orders containing a book |
| `SUM(x)` | sum | revenue (`quantity * unit_price`) |
| `AVG(x)` | average | average price |
| `MIN(x)` / `MAX(x)` | extremes | cheapest / most expensive book |

`GROUP BY column` splits the rows into groups (one per value of the column) and every function works **inside** the group. `HAVING` filters the groups *after* aggregation (while `WHERE` filters the rows *before*).

A "well-made" API does not make you download 300 rows of `order_items` to add them up on the client: it exposes an endpoint that does the calculation in the database and returns only the result. It is faster and, above all, the result is **consistent** (a single source of truth).

<Aside type="note" title="Which tables do the numbers come from?">
`/stats/sales` joins **four** tables: `orders` (date and status) → `order_items` (quantity and price) → `books` (category, author) → `categories`/`authors`/`customers` depending on `group_by`. You will see the exact query in chapter 12 when you write it yourself with `/sql`.
</Aside>

Three aggregated columns per group: `orders` is `COUNT(DISTINCT o.id)` (an order with 3 lines counts once), `books_sold` is `SUM(oi.quantity)`, `revenue` is `SUM(oi.quantity * oi.unit_price)`. `cancelled` orders are excluded by a `WHERE` before grouping.

## Python and TypeScript

Sales per city, turned into a text bar chart. The heavy lifting (sums and groupings) is done by the server; the client only sorts and draws.

<Tabs syncKey="lang">
<TabItem label="Python">
```python
# pip install httpx   →   python3 vendite.py
import httpx

BASE = "https://corso-api-json.giuseppebosi.com/api/v1"
r = httpx.get(f"{BASE}/stats/sales", params={"group_by": "city"}, timeout=10)
r.raise_for_status()                       # solleva un'eccezione se lo status non è 2xx
righe = r.json()["items"]
massimo = max(x["revenue"] for x in righe)
for x in sorted(righe, key=lambda x: -x["revenue"]):
    barra = "█" * round(30 * x["revenue"] / massimo)
    print(f"{x['city']:<8} {barra:<30} {x['revenue']:>8.2f} € ({x['orders']} ordini)")
```
</TabItem>
<TabItem label="TypeScript">
```ts
// node --experimental-strip-types vendite.ts
const BASE = "https://corso-api-json.giuseppebosi.com/api/v1";
type Riga = { city: string; orders: number; books_sold: number; revenue: number };

const r = await fetch(`${BASE}/stats/sales?group_by=city`);
if (!r.ok) throw new Error(`HTTP ${r.status}`);
const { items } = (await r.json()) as { items: Riga[] };
const massimo = Math.max(...items.map((x) => x.revenue));
for (const x of [...items].sort((a, b) => b.revenue - a.revenue)) {
  const barra = "█".repeat(Math.round((30 * x.revenue) / massimo));
  console.log(`${x.city.padEnd(8)} ${barra.padEnd(30)} ${x.revenue.toFixed(2).padStart(8)} € (${x.orders} ordini)`);
}
```
</TabItem>

## Exercise

1. Which category has the highest **revenue**? Is it the same one with the most **books sold**? (use `group_by=category`).
2. Write a script that calls `/stats/sales?group_by=month` and prints the best and the worst month.
3. Why does `orders` in `/stats/sales` use `COUNT(DISTINCT o.id)` and not `COUNT(*)`?

<details>
<summary>Solution</summary>

1. With `group_by=category`: **saggistica** (non-fiction) has the highest revenue (€1,489.55) **and is also first for copies sold** (82), followed by narrativa (fiction: €1,460.82 and 64 copies). Here the two rankings coincide, but it is not a given: further down, cucina (cooking) sells 39 copies with lower revenue (€742.25) than fantascienza (sci-fi), which sells 28 (€834.10). It depends on the average price.
2. Once you have `items`, `max(items, key=lambda x: x["revenue"])` and `min(...)` in Python; in TS sort with `sort` and take the first and the last.
3. Because the query joins `orders` with `order_items`: an order with three lines appears three times in the JOIN. `COUNT(*)` would count the rows, `COUNT(DISTINCT o.id)` the orders.
</details>

## Common mistakes

- **Aggregating on the client** by downloading every row: slow, and with pagination you risk adding up only the first page.
- **Confusing `WHERE` and `HAVING`**: `from`/`to` filter the *rows* (WHERE), "only categories with more than 5 books" filters the *groups* (HAVING).
- **Forgetting the statuses**: revenue that includes cancelled orders is wrong. Always ask the API (or the documentation) what it excludes.
- **Averages of averages**: the average of the per-category average prices is not the average price of the catalog.

## Summary

Aggregations are numbers computed by the database over groups of rows; the API exposes them as dedicated endpoints (`/stats`, `/stats/sales`) with parameters to choose the grouping and the period. In the next chapter you switch sides: you will build the query yourself, in JSON, with `POST /query`.
