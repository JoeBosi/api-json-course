## Obiettivi

- Capire quando una colonna JSON è una buona idea in un database relazionale (e quando no).
- Interrogare JSON dentro SQLite: `json_extract`, `->>`, `json_each`, `json_type`, `json_object`.
- Usare le tre porte che l'API offre sulla colonna `books.attributes`: filtro `?format=`, campi `attributes.*` in `/query`, SQL in `/sql`.
- Sapere cosa cambia in PostgreSQL (`jsonb`) e in un database a documenti (MongoDB).

## Teoria

La tabella `books` ha colonne "normali" (`title`, `price`, `author_id`…) e una colonna `attributes` che contiene **testo JSON**:

```json
{"format": "brossura", "cover": "morbida", "awards": [], "dimensions_cm": {"w": 15, "h": 19}, "ebook": false}
```

Perché non fare una colonna per ogni attributo? Perché gli attributi sono **eterogenei e mutevoli**: i libri di informatica hanno `edition`, i romanzi no; domani arriva `audio_minutes`. Una colonna JSON accoglie tutto senza `ALTER TABLE`. Il prezzo: niente vincolo di tipo per chiave, query più lente se non indicizzate, e la tentazione di metterci dentro anche ciò che dovrebbe essere una colonna (o una tabella) vera.

Regola pratica: **colonna normale** per ciò su cui filtri, ordini, fai join o vincoli (prezzo, autore, stato); **colonna JSON** per proprietà descrittive, variabili, "a coda lunga".

### Le funzioni JSON di SQLite

SQLite (dalla 3.38 sempre inclusa) offre:

| Funzione / operatore | Cosa fa |
|---|---|
| `json_extract(col, '$.a.b')` | estrae un valore per percorso; `$` è la radice |
| `col ->> '$.a'` | come `json_extract`, ma restituisce sempre un valore SQL (testo/numero); `->` restituisce JSON |
| `json_type(col, '$.a')` | il tipo JSON: `text`, `integer`, `real`, `true`, `false`, `null`, `array`, `object` |
| `json_each(col, '$.arr')` | **tabella virtuale**: una riga per ogni elemento di un array (si mette nel `FROM`) |
| `json_array_length`, `json_valid`, `json_object`, `json_group_array` | lunghezza, validità, costruzione di JSON da righe SQL |

E il dettaglio che fa la differenza in produzione: puoi creare un **indice su un'espressione**, ad esempio `CREATE INDEX idx_format ON books(attributes ->> '$.format')`, così un filtro sul formato non scandisce tutta la tabella.

Altre tre query da provare (stesso schema di chiamata):

```sql
-- tipi dei valori JSON
SELECT json_type(attributes, '$.awards') AS t_awards, json_type(attributes, '$.ebook') AS t_ebook,
       json_array_length(attributes, '$.awards') AS n FROM books WHERE id = 1;
-- → [["array","false",0]]

-- JSON dentro un'altra colonna JSON: l'indirizzo degli ordini
SELECT json_extract(shipping_address, '$.city') AS city, COUNT(*) AS n
FROM orders GROUP BY 1 ORDER BY n DESC LIMIT 3;
-- → [["Torino",25],["Padova",22],["Firenze",19]]

-- costruire JSON da righe relazionali: il libro con i suoi tag (tabella N-N) in un documento
SELECT json_object('id', id, 'title', title,
  'tags', (SELECT json_group_array(t.name) FROM tags t JOIN book_tags bt ON bt.tag_id = t.id WHERE bt.book_id = b.id)) AS doc
FROM books b WHERE id IN (1, 2);
-- → {"id":2,"title":"TypeScript e Ferrara","tags":["bestseller","tascabile"]}
```

L'ultima è interessante: è **esattamente ciò che fa un'API** quando risponde `GET /books/2?expand=tags`. Il JSON che ricevi dall'API nasce così, da un join tradotto in documento.

```python
import httpx
BASE = "https://corso-api-json.giuseppebosi.com/api/v1"

# 1) filtro dedicato: l'API traduce ?format= in json_extract(attributes,'$.format') = ?
r = httpx.get(f"{BASE}/books", params={"format": "rilegato", "limit": 2}).json()
print(r["meta"]["total"], [b["title"] for b in r["items"]])
# 24 ['Andromeda e il Novecento', 'Le mura di Norcia']

# 2) query strutturata: campi "attributes.x" ammessi nel where e nel select
q = {"from": "books", "select": ["id", "title", "price", "attributes.format"],
     "where": {"and": [{"field": "attributes.format", "op": "eq", "value": "tascabile"},
                       {"field": "price", "op": "lt", "value": 10}]},
     "order_by": ["price"], "limit": 3}
r = httpx.post(f"{BASE}/query", json=q).json()
print(r["meta"]["sql"])      # guarda come è stato tradotto
for b in r["items"]:
    print(b["price"], b["title"], b["attributes.format"])

# 3) SQL libero (solo SELECT): json_each per "esplodere" un array
sql = "SELECT b.title, j.value AS award FROM books b, json_each(b.attributes, '$.awards') j LIMIT 4"
r = httpx.post(f"{BASE}/sql", json={"sql": sql}).json()
print(r["columns"], r["rows"])
```

7.25 Contro Aosta tascabile

Vuoi provare le stesse funzioni **in locale**, senza server? `sqlite3` è nella libreria standard:
```python
import sqlite3, json
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE b(title, attributes)")
con.execute("INSERT INTO b VALUES (?, ?)", ("Prova", json.dumps({"format": "ebook", "awards": ["Strega"]})))
con.execute("CREATE INDEX i ON b(attributes ->> '$.format')")   # indice su espressione
print(con.execute("SELECT title, attributes ->> '$.format', json_array_length(attributes, '$.awards') FROM b").fetchall())
# [('Prova', 'ebook', 1)]
```

<Aside type="note" title="PostgreSQL e MongoDB, in breve">
**PostgreSQL** ha due tipi: `json` (testo conservato com'è) e **`jsonb`** (binario, normalizzato, indicizzabile). Operatori: `->` (JSON), `->>` (testo), `@>` (contenimento: `attributes @> '{"format":"tascabile"}'`), `?` (esiste la chiave). Un **indice GIN** su una colonna `jsonb` accelera `@>` e `?` su qualunque chiave, senza dover scegliere prima. È il motivo per cui "Postgres + jsonb" copre molti casi in cui prima si sceglieva un database a documenti.
**MongoDB** ribalta il modello: il documento JSON (BSON) *è* la riga; le query sono JSON (`{ "attributes.format": "tascabile", price: { $lt: 10 } }`) e le relazioni si esprimono annidando o con `$lookup`.
</Aside>

## Esercizio

1. Con `/sql`: quanti libri hanno **almeno un premio**? (suggerimento: `json_array_length(attributes, '$.awards') > 0`).
2. Con `/sql`: l'altezza media (`dimensions_cm.h`) dei libri per formato.
3. Con `/query`: i libri in formato `rilegato` **oppure** con `ebook = true`, ordinati per prezzo decrescente, primi 5.

<details>
<summary>Soluzione</summary>

```sql
SELECT COUNT(*) FROM books WHERE json_array_length(attributes, '$.awards') > 0;   -- 29
SELECT attributes ->> '$.format' AS f, ROUND(AVG(attributes ->> '$.dimensions_cm.h'), 1) AS h FROM books GROUP BY 1;
-- brossura 20.7 · rilegato 21.1 · tascabile 21.1
```
```json
{"from": "books", "where": {"or": [{"field": "attributes.format", "op": "eq", "value": "rilegato"},
                                    {"field": "attributes.ebook", "op": "eq", "value": true}]},
 "order_by": ["-price"], "limit": 5}
```
(prezzi 34.36, 33.45, 32.71, 31.27, 31.04). Nota nella seconda query: `->>` restituisce un numero quando il valore JSON è numerico, quindi `AVG` funziona senza cast.
</details>

## Errori comuni

- **`json_extract(col, 'format')`** senza `$.`: il percorso deve iniziare dalla radice `$`.
- **Confrontare `->` con una stringa**: `->` restituisce JSON (con le virgolette!), `->>` il valore. Per i `WHERE` usa quasi sempre `->>`.
- **Booleani**: in SQLite `true`/`false` JSON diventano `1`/`0` con `->>` (lo vedi nel widget sopra: `attributes.ebook: 1`); `json_type` invece dice `true`/`false`.
- **Tutto in JSON**: se filtri e fai join su una chiave ogni giorno, promuovila a colonna (o tabella) vera.
- **Dimenticare l'indice su espressione** quando la colonna JSON cresce: la query resta corretta ma scandisce tutta la tabella.

## In sintesi

Una colonna JSON dà flessibilità dove lo schema è variabile; SQLite e PostgreSQL sanno estrarre, filtrare, esplodere e indicizzare quel JSON, e un'API buona espone quelle capacità in modo controllato. Nel prossimo capitolo: JSON sul filo HTTP, header, body ed errori.
